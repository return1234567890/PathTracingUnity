# 路径追踪管线接入体积雾的可行性调研

> 调研对象：URPPT — Unity 2022.3.62f3c1 + URP 14.0.12 + Vulkan Ray Query 路径追踪 + DLSS Ray Reconstruction
> 调研时间：2026-11-21
> 调研范围：只回答「当前 PT 管线能不能接入体积雾、有几种接法、各自代价多大、先做哪一种」。
> 不评估：美术侧的雾参数调校流程、体积云/行星级大气散射的物理模型、与 Terrain 加速结构 / RT pipeline 迁移的先后次序（§13 只给一句结论）。
> 调研方法：**静态代码审计**（工作区 HEAD `6260b2c` + 未提交改动，`pathtrace.glsl` 共 1270 行）+ **CPU 数学探针**（`Tools/fog_math_probe.py`，结果 `Tools/fog_math_probe_results.txt`）+ NGX SDK 头文件比对 + 公开资料交叉验证。
> **本机没有做过 Unity 侧的体积雾原型**：§5 的介质数学已在 CPU 上验证通过，但所有性能数字都是按代码结构推算，逐条标注「未实测」；凡标 ⚠️ 的判定都需要 §10 的实测来关闭。

## 1. 结论速览

**一句话：技术可行，而且比「加一个新 Pass」更省——体积雾可以直接长在现有 PT 主循环里，复用已有的阴影射线与彩色玻璃透射，改一个 UBO + 主循环即可落地。真正的不确定项不是「能不能做」，而是「1spp + DLSS RR 能不能吃下雾的噪声」。**

| 维度 | 判定 | 依据 |
|---|---|---|
| 技术路线匹配 | ✅ 高 | 主循环已有「段」（segment）概念与 Beer-Lambert 乘子（`pathtrace.glsl:1066-1070`），雾只需把「玻璃内吸收」推广成「全局解析介质 + 自由程采样」；阴影射线已能返回**彩色**玻璃透射（`:568-706`），天然产出彩色光束 |
| 与 DLSS RR 的兼容性 | ⚠️ 未验证（最大风险） | 雾若写进 `outputImg`，RR 的 6 张 guide 全部按「表面」语义解释（`vpt_dlss.cpp:784-826`）；雾噪声是否在 RR 训练分布内，必须实测 |
| 改动面 | ✅ 小 | P1–P3 全程 **0 张新输出图、0 个新 binding、0 个新 Pass**；只扩 UBO（208B → 256B）+ 改 `pathtrace.glsl` 主循环 |
| 性能 | ⚠️ 中，未实测 | 估算 PT 段 **+25% ~ +45%**（同 spp）；若 1spp 噪声不达标要提到 2spp，则近似翻倍 |
| 显存 | ✅ 可忽略 | +48B UBO，无 3D 纹理、无额外 RT |
| 观感收益 | ✅ 高 | 「教堂彩窗 + 阳光」正是体积雾最出效果、也最匹配现有资产的用例 |
| 工作量（粗估） | **7.5 ~ 11 人天**（仅全局介质） | 加做局部雾盒再 +1.5 ~ 2.5、不均匀流动再 +2 ~ 3.5；不含可选 froxel 路线（再 +8 ~ 12 人天） |

**关键数字（先看这五条，出处见 §6）**

| 内容 | 数值 | 条件 |
|---|---|---|
| 最近一次 Play 的 PT 配置 | `maxDepth=4, spp=1, DLSS_RR=开(Balanced 1.7×), env=default` | `Editor.log` 的 `[PathTrace] PT 配置` 行 |
| 渲染分辨率 | 568×320（该次会话口径；与 Terrain 文档的 960×540 冲突，见 §6.1） | 同上日志 + `doc/RT_pipeline整体切换可行性调研.md` §1 |
| 新增参数体积 | UBO +48B（`VPT_CameraData` 192B → 240B，UBO 208B → 256B） | `vpt_dispatch.cpp:104-117` |
| 新增光线数 | **0 根 closest-hit、0 根净增 shadow ray**（散射事件替换表面 NEE） | §6.3 推演 |
| 介质数学 | **CPU 探针全部 PASS**：解析 τ 相对误差 ≤1.3e-7、自由程反演偏差 3.9e-4 | `Tools/fog_math_probe_results.txt` |
| 场景接入 | 薄雾 = 3 个 UBO 标量；局部雾团 = **0 个 BLAS、0 个 TLAS 实例**、1 个新 SSBO | §12 |
| 估算 PT 段增量 | +25% ~ +45%（同 spp）；提到 2spp 则 +150% ~ +190% | **未实测**，§6.4 |

**五条推荐线（不要「视情况而定」）**

- **只要「彩窗光束 / 丁达尔」**→ 直接做 **形态 E（Portal 光柱，§4.6）**。**3 ~ 4 人天**，零噪声、零 RR 风险、窄光束也能出（样本强制落在柱体内），代价是要标窗口。**这是本调研对「只做丁达尔」的正式推荐。**
- 只想要「远景发灰、有空气感」→ 做 **P1 = 形态 A（解析吸收 + 天空 in-scatter）**。P1 本身 1.5 ~ 2.5 人天，**含基线验证约 2.5 ~ 3.5 人天**，零噪声，当天可见效果，不动 RR。
- 想要「丁达尔但不想标窗口 / 光柱形状不规则」→ 做到 **P2 = 形态 B（单次散射 + NEE）**。累计 **6 ~ 9 人天**，通用性最强，但会引入噪声与 RR 风险，窄光束基本无效（§5.14）。
- 想要「真体积雾（浓雾包裹物体、雾中发光体、多次散射）」→ 才做 **P3 = 形态 C**，累计 **7.5 ~ 11 人天**，且必须先过 §10 的 RR 噪声门槛；过不了就**退回 P2**，别硬上。
- 想要「不均匀 + 流动」（雾团漂移、翻滚细节）→ 按 §12.4 的三层配方叠加：**L0 解析薄雾 + L1 局部雾盒 + L2 3D 纹理细节**。注意 §12.5 的成本阶梯：**硬边常数密度盒仍可解析**，只有软边 falloff / 噪声 / 纹理才退化成 ratio tracking；L2 还要先过 §12.6 的「流动 vs RR 拖影」验证。
- 明确不建议：① 用 URP 内置雾 / `RenderSettings.fog`（PT 路径下被彻底旁路，§3.4）；② 一上来就做 froxel 体积雾（没有 shadow map，逐 froxel 遮挡要么做不出光束、要么贵到离谱，§4.4）；③ 把雾盒当 AABB 送进 TLAS（§12.8：硬件给不了透射率，还要 N+1 次遍历，且会撞上现有两处「只认三角形」的候选分支）。

## 2. 先澄清「体积雾」的三种含义

这个词在本项目里会被估错一个数量级，先拆开。

| # | 含义 | 视觉 | 需要的物理量 | 对应形态 | 工作量比 |
|---|---|---|---|---|---|
| 2.1 | **大气透视**（aerial perspective） | 远处变灰、对比度下降、天空发白 | 消光 `σt` + 天空/环境 in-scatter | 形态 A | 1× |
| 2.2 | **光源体积散射**（丁达尔 / light shaft） | 彩窗投下的彩色光柱、灯的光锥 | 单次散射 + 相函数 + 光源可见性 | 形态 B | 3× |
| 2.3 | **真参与介质**（高度雾 / 局部雾体积 / 体积云） | 雾能包住物体、雾里物体互相照亮、浓雾看不清远景 | 自由程采样 + 相函数 + 路径延续（多次散射） | 形态 C | 6 ~ 10× |

本轮调研的默认目标按 **2.2** 评估（教堂场景 + 彩窗 + 平行光是本项目最值钱的组合），同时把 2.1 / 2.3 的增量路径写清。

## 3. 项目现状：为什么现在一点雾都没有

### 3.1 一帧 PT 的完整数据流（C# → native → shader）

```
Game Camera（PathTraceCameraGate 已把 cullingMask 置 0、关后处理、关阴影：PathTraceCameraGate.cs:96-103）
  └─ PathTraceRenderPass.Execute  [RenderPassEvent.AfterRenderingPostProcessing = 600，PathTraceRendererFeature.cs:155-158]
       ├─ EnsureRTs：7 张 RT（output / gbuffer0 / gbuffer1 / diffuseAlbedo / specularAlbedo / motionVector / linearDepth）
       ├─ VPT_PrepareDispatch(RTs, camData)            [vpt_dispatch.cpp:390]   ← 主线程：填 UBO + 写 18 个描述符
       ├─ IssuePluginEvent(EVENT_PATHTRACE=1)          [vpt_dispatch.cpp:640]   ← 渲染线程：barrier + vkCmdDispatch
       ├─ DlssAux MotionVector kernel                  [Assets/Shaders/DlssAux.compute]
       ├─ VPT_DLSS_PrepareRRDispatch + EVENT_DLSS=2    [vpt_dlss.cpp:745]
       └─ cmd.Blit(outputRT 或 dlssOutputRT → cameraColorTarget)
```

关键事实：**整条链路只认「表面命中」与「miss」两种结局**，没有任何「介质」概念；`outputImg` 是 rgba16f 线性 HDR，`gbufferPosDepth` 是 rgba32f（`xyz` = 世界坐标，`w` = 射线距离 `hitT`，`pathtrace.glsl:1076`）。

### 3.2 现有的「体积」是玻璃内部的 Beer-Lambert，不是参与介质

这是最容易误判的一点：代码里到处是 `volume` / `sigmaT` / `attenuation`，但它**只做吸收，不做散射**，且只在玻璃**内部**生效。

| 事实 | 位置 | 说明 |
|---|---|---|
| `MAT_IS_VOLUME`（bit5）只由 `thickness > 0` 判定 | `pathtrace.glsl:363-366`、`ModelManager.cs:812-825` | `thickness` 是**开关**，不参与吸收距离 |
| `σt` 由 `attenuationDistance` 反推 | `pathtrace.glsl:376-382`：`σt = -ln(clamp(tint·attenuationColor,1e-4,1))/attenuationDistance` | 材质级常量 |
| 吸收只在 `isInsideVolume` 时乘 | `pathtrace.glsl:1069-1070`：`throughput *= exp(-hit.hitT * volumeSigma)` | 每段一次 |
| 介质状态机是 1 bit | `pathtrace.glsl:946-947`（`bool isInsideVolume` + `vec3 volumeSigma`）、`:1229-1244` 翻转 | 单介质假设，无嵌套 |
| 阴影侧同样只做吸收 | `pathtrace.glsl:640-641` | 无散射项 |

`doc/PT半透明材质渲染流程.md` §8-①② 已经把「单介质假设」「`thickness` 只是开关」写成已知限制。**结论：它是「有色玻璃的吸收」，不能复用为雾**——缺的是散射、相函数、自由程、全局密度场四件东西。

### 3.3 没有散射 / 相函数 / 自由程（grep 证据）

对 `NativePlugin/shaders/pathtrace.glsl` 全文搜索 `scatter|phase|henyey|hg|freeflight|majorant|tracking|participat`，**零命中**；搜索 `fog` 亦零命中。也就是说：不是「已有实现要接」，而是**从零加一套介质积分**。反过来说，正因为没有历史包袱，插入点很干净（§5）。

### 3.4 URP 的雾与深度在 PT 路径下被彻底旁路

| 事实 | 证据 |
|---|---|
| `RenderSettings.fog` 无人读取 | 全工程 `.cs` grep `RenderSettings` / `fog` 无消费点；场景 `SampleScene.unity` 里 `m_Fog: 0` |
| 光栅几乎什么都不画 | `PathTraceCameraGate.cs:96-99`：`cullingMask = 0`、`renderPostProcessing = false`、`renderShadows = false`；`URP-PathTrace-Renderer.asset:51-56` 的 Opaque/Transparent LayerMask 均为 0 |
| 没有 `_CameraDepthTexture` | `URP-HighFidelity.asset:23-24`：`m_RequireDepthTexture: 0`；PT Pass 无 `ConfigureInput(...)` |
| PT 自己的深度不是 NDC 深度 | `_gbuffer0.a = hitT`（世界单位射线距离，`pathtrace.glsl:1076`）；`_linearDepthRT = clip.w` 且**只在 `dlssEnabled` 时创建**（`PathTraceRendererFeature.cs:745-750`） |

**结论：任何「基于 URP `_CameraDepthTexture` 的全屏体积雾」在本项目里没有输入，不可行。** 要做雾，深度只能取自 PT 的 `_gbuffer0`（世界坐标 + 距离），还必须自己处理低分辨率上采样与行翻转（PT 在 shader 内做 Y 翻转，`pathtrace.glsl:1267-1269`）。

### 3.5 DLSS RR 的输入语义与雾的冲突（这条决定「雾放哪里」）

RR 消费 6 张 guide，全部是「表面」语义：

| RR 输入 | 来源 | 雾覆盖该像素时的语义 | 位置 |
|---|---|---|---|
| color | `_outputRT`（ARGBHalf） | 雾会混进来 | `vpt_dlss.cpp:784-786` |
| depth | `_linearDepthRT`（RFloat） | 仍是**表面**距离，不是雾的等效深度 | `:792-794`、`DlssAux.compute:68-70` |
| motion | `_motionVectorRT`（RGFloat，UV 空间） | 表面 reproject，不含雾的自身运动 | `:788-790` |
| normal + roughness | `_gbuffer1`（打包） | 仍是命中表面法线 | `:804-806` |
| diffuse albedo | `_diffuseAlbedoRT` = `albedo·(1-metallic)` | 雾没有 albedo 通道 | `:808-810`、`pathtrace.glsl:1083-1084` |
| specular albedo | `_specularAlbedoRT` = `EnvBRDFApprox(...)` | 同上 | `:812-814`、`pathtrace.glsl:1085-1086` |

`doc/PT半透明材质渲染流程.md` §8-⑦ 已经踩过一次同类问题（「RR 把首次命中当不透明表面」→ 玻璃边缘模糊/拖影）。**体积雾会把这个问题放大**：雾覆盖的像素占比远大于玻璃。

反过来，NGX DLSSD 还留了「雾」与「命中距离」两组可选通道，本项目一处未用：

- `pInColorBeforeFog` / `pInColorAfterFog`（`NativePlugin/third_party/ngx/include/nvsdk_ngx_helpers_dlssd_vk.h:67-68`，参数下发 `:290-291`）
- `pInDiffuseHitDistance` / `pInSpecularHitDistance`（`:78-79`，参数下发 `:302-303`）
- `grep pInColorBeforeFog|pInDiffuseHitDistance NativePlugin/src/vpt_dlss.cpp` → **零命中**

这两组通道的存在说明「雾在 RT 之外合成、把雾前/雾后两张颜色一起喂给 RR」是 NVIDIA 官方支持的形态（RR 借此区分雾与被雾遮蔽的细节）。**但 Vulkan 后端是否真的消费、接入后能改善多少，未验证**——这是形态 D 的唯一官方依据，也是失败时的退路。

### 3.6 可扩展性现状（决定改动成本）

| 项 | 现状 | 加雾的成本 |
|---|---|---|
| 参数 | 单 UBO 208B，std140 + row_major（`vpt_dispatch.cpp:104-117` ↔ `pathtrace.glsl:39-50`） | ✅ 便宜：扩 3 个 vec4 |
| 描述符 | 1 个 set、18 binding、`maxSets=1`、池尺寸写死（`:129-196`） | ⚠️ 加 binding 要改 6 处硬编码下标 |
| 输出图 | `s_OutputViews[5]` 写死，6 处 `i<5` 循环（`:43、:480、:538、:817、:860、:874`） | ❌ 加图最贵 |
| Push constant / bindless | 都没有 | — |

**体积雾恰好只需要参数**：不新增图像、不新增 binding、不加 Pass。这是本方案能被判为「小改动」的核心原因。

## 4. 五种接入形态对比

### 4.1 形态 A：PT 内解析介质（吸收 + 天空 in-scatter，零随机）
每个段用解析式乘一个透射率，miss 分支再乘天空透射率并补一项天空 in-scatter。**没有新随机数、没有新光线、零噪声**。对应 §2.1。

### 4.2 形态 B：PT 内单次散射（1 次自由程采样 + NEE + 相函数）
每段采样一个散射距离；若落在段内，则在该点做一次 NEE（复用现有阴影射线与彩色玻璃透射），得到彩色光柱，然后**终止该路径**（单次散射近似）。对应 §2.2。

### 4.3 形态 C：PT 内真参与介质（路径延续）
与 B 相同，但散射事件后**不终止**，继续按相函数弹射，得到多次散射（浓雾包裹、雾中互照）。需要散射次数上限与 RR 预算。对应 §2.3。

### 4.4 形态 D：PT 之外（froxel / 全屏后处理）
独立 compute 做视锥 froxel 体积雾，或用全屏 shader 按深度做距离雾，再与 PT 结果合成。**问题**：① froxel 的散射需要「每个 froxel 的光源可见性」，本项目没有 shadow map，只能逐 froxel 打阴影射线（568×320 下 64 层 froxel ≈ 92 万条，是现有阴影射线的 2 倍以上），或者干脆不做遮挡（那就没有彩窗光束，等于白做）；② 全屏后处理只有距离雾，没有光束；③ 两种做法都要面对 §3.5 的 RR 语义问题，且必须用 `ColorBeforeFog/ColorAfterFog` 才能不把 RR 带偏。

### 4.5 对比总表

| 维度 | A 解析吸收 | B 单次散射 | C 真介质 | D froxel/后处理 |
|---|---|---|---|---|
| 大气透视 | ✅ | ✅ | ✅ | ✅ |
| 光束（丁达尔） | ❌ | ✅ 彩色 | ✅ 彩色 | ⚠️ 需逐 froxel 遮挡 |
| 多次散射 | ❌ | ❌ | ✅ | ✅（限 froxel 分辨率） |
| 物理正确性 | 中（只有消光） | 中高（单散射） | 高 | 低（屏幕空间近似） |
| 雾参与 GI / 反射 | ❌ | ⚠️ 部分（只进主路径） | ✅ | ❌ |
| 噪声 | **零** | 有（1spp 明显） | 有（更明显） | 低（可模糊/时域） |
| 与 RR 的关系 | 不改变语义（只有衰减） | ⚠️ 需实测 | ⚠️ 需实测 | 需用 ColorBeforeFog 通道 |
| 新增光线 | 0 | 0（净） | 0（净） | 约 1 条/froxel |
| 改动面 | 主循环 3 处 + UBO | + 相函数 + 散射分支 | + 终止策略 + maxDepth 预算 | 新 Pass + 新 pipeline + 新事件 + 新 RT |
| 显存 | +48B | +48B | +48B | +数 MB（froxel 3D 图） |
| 工作量 | 2.5 ~ 3.5 d（含基线） | 累计 6 ~ 9 d | 累计 7.5 ~ 11 d | 8 ~ 12 d（且大概率不是首选） |
| 建议 | ✅ 第一步 | ✅ **推荐落点** | ⚠️ 视 RR 实测 | ❌ 不作为首选 |

> **如果目标只有丁达尔效应**（不要大气透视、不要雾团、不要体积云），上面四档都不必选——直接用 **§4.6 的形态 E（Portal 光柱）**：零噪声、零 RR 风险、约 3 ~ 4 人天。

### 4.6 形态 E：Portal 光柱（只做丁达尔时的推荐方案）

**核心洞察：只要丁达尔，就不需要「介质积分」，只需要「窗口挤出的柱体里的单次散射」。**

前面所有方案的复杂度都来自「通用介质」：吸收、多次散射、非均匀密度、跟踪、与玻璃状态机共存。但丁达尔效应严格来说只有一件事——**视线在某个体积里，那个体积被光穿过，于是多了一份散射辐亮度**。而这个体积对「平行光 + 矩形窗」是**解析可描述的**（§5.13 的斜棱柱），于是整个问题可以退化成：

```
对每个窗口 portal：
  求视线在该柱体内的区间 [t0, t1]        ← 5 个半空间夹逼，零遍历（不是 4 个平面）
  在区间内放 4 个样本，各自算：
       T(t)（雾的透射，§5.2 解析式）
       σs·p(θ)·L_sun                     ← 相函数 + 太阳
       可见性（可选：1 条朝太阳的阴影射线）
  按 (t1−t0)/4 加权求和，直接加到 radiance
```

**为什么是 5 个半空间而不是 4 个平面**：光束的边界不是 4 个平面，而是「窗口矩形沿太阳方向斜着挤出来」的柱体——它的 4 个侧面是被**剪切**过的（斜的），第 5 个面是窗口本身所在的平面。把「求视线在柱体内的区间」写成 5 条线性不等式，比逐个平面求交更简单也更稳（推导见 §4.7）。

**为什么这是「性能与效果」的最优解**（和另外三条对比）：

| 方案 | 每像素新增阴影射线 | 噪声 | 窄光束（§5.14） | RR 风险 | 需要美术 | 实现量 |
|---|---|---|---|---|---|---|
| B 自由程采样 | 0（净） | **高** | ❌ 命中率 ∝ 弦长 | **高**（全案唯一需实测项） | 否 | 中 |
| B′ 全线均匀求积 16 步 | 16 | 0 | ⚠️ 步长 2 m 时细缝会被跨过 | 低 | 否 | 中 |
| **E Portal 支持域 4 点求积** | **0 ~ 4**（朝太阳，方向全同 → 极相干） | **0** | ✅ 样本强制落在柱体内，与宽度无关 | **低**（确定性、平滑） | ✅ 标窗口 | 中低（3~4 d） |
| 屏幕空间径向模糊 | 0 | 0（但要额外 mask） | ✅ | 中（后处理绕过 RR，进不了反射） | 否 | 低 |

E 的四个决定性优势：

1. **彻底绕开全案最大的风险**——没有随机采样就没有体积噪声，也就不需要「RR 能不能吃下雾噪声」这场 A/B（§10.2 的 #4/#5 直接作废）；
2. **窄光束不再是问题**：样本按 `[t0,t1]` 等距放，不是按自由程抽，宽度只影响积分区间，不影响命中率（§5.14 的病根被移除）；
3. **不需要通用介质的那一整套机器**：不改 `isInsideVolume` 状态机、不改 G-buffer / RR guide 语义、不动 `maxDepth`、不需要 ratio tracking、不需要 3D 纹理；
4. **成本可控且可分级**：0 条阴影射线（不挡柱子）→ 2 条（弱遮挡）→ 4 条（柱子投影准确），按需要选。

**限制（必须和美术说清楚）**：

- **不是通用介质**：没有远景大气透视、没有雾团、没有多次散射、没有「雾里物体互相照亮」。浓雾下核心会偏亮、偏平（缺多次散射）——这正是「只做丁达尔」的定义；
- **要标 portal**：每扇窗一个矩形（4 角点）+ 太阳方向 + 玻璃颜色。教堂通常是 3 ~ 8 扇，工作量可控；也可以写个编辑器工具从窗口 mesh 自动生成包围矩形；
- **只对平行光成立**：本项目的太阳正好是平行光（`pathtrace.glsl:715-719`）。点光/聚光需要另做（体积锥，公式不同）；
- **遮挡需要额外代价**：不测可见性时，光柱会穿过柱子/家具。教堂内部有柱子和拱券，建议至少 2 个可见性样本；从**中点**取 1 个样本会让柱子投影变成「整束全黑」，很假；
- **默认只加到主光线**：反射/折射里看不到光柱。要的话把同一个函数在次级射线上再调一次（成本 × 弹射数）；本项目彩色玻璃的反射里光柱不明显，可以先不做。

**一个几乎免费的加分项：光束带花纹。** 把每个样本沿太阳方向投影到 portal 平面取 UV，直接采样该窗的 `baseColorTex`（`pathtrace.glsl:119`），就得到「玫瑰窗的花纹浮在空气里」——每样本 1 次纹理采样，比走 `traceShadowTransmission` 遍历玻璃还便宜。这是教堂场景最值得做的视觉细节。

**工作量**：C# portal 组件 + Manager（照 `LightManager`，§12.3）、native 加一个 portal SSBO（binding 18）、GLSL 裁剪 + 4 点求积 + 相函数 ≈ **3 ~ 4 人天**（含调参与验证），**比形态 B 更少**（不需要采样机器、不需要 RR A/B、不需要 maxDepth 预算）。

> 选择建议一句话：**「只要丁达尔」→ 形态 E；「丁达尔 + 远景空气感」→ E + 形态 A；「要真雾」→ 才回到 B/C。**

### 4.7 形态 E 的算法全流程（原理版）

这一节把 §4.6 的一行伪代码展开成可实现、可验算的五步。**全部是解析式，没有任何随机数与遍历。**

#### 4.7.1 输入：一个 portal 是什么

一个 portal 描述一扇窗（或任意透光矩形）：

| 量 | 含义 | 用途 |
|---|---|---|
| `C` | 矩形中心（世界） | 定位 |
| `e1`, `e2` | 平面内两个单位轴 | 定义「窗内/窗外」 |
| `w2`, `h2` | 半宽、半高（m） | 同上 |
| `n` | **外法线**（从室内指向太阳那一侧），`L·n > 0` | 区分室内外 |
| `L` | 太阳方向（指向太阳，单位向量） | 光束方向 |
| `K` | 玻璃透射色（RGB），可选纹理 + UV 范围 + alpha 阈值 | 光束颜色/花纹 |
| `E_sun` | 太阳辐亮度（可来自现有 `lights[]` 的 directional 项） | 强度 |

96B/portal（6 × `vec4`），与 §12.3 的雾盒共用同一个 SSBO（`binding = 18`）也放得下。

#### 4.7.2 第 1 步：把「斜柱体」写成 5 个半空间

**几何定义**：点 `P` 在光束内 ⟺ 从 `P` 朝太阳方向 `L` 走，能穿过窗口矩形。

先把 `P` 投到窗面上：`τ(P) = −(P−C)·n / (L·n)`（要求 `τ ≥ 0`），落点 `Q = P + τ(P)·L`。再要求 `Q` 在矩形内，即 `|(Q−C)·e1| ≤ w2`、`|(Q−C)·e2| ≤ h2`。

把 `τ` 代进去，`Q` 的平面内坐标变成 `P` 的**线性**函数：

```
q1(P) = (P−C)·a1 ,  a1 = e1 − n·(L·e1)/(L·n)
q2(P) = (P−C)·a2 ,  a2 = e2 − n·(L·e2)/(L·n)
```

于是光束 = **5 个线性不等式的交集**：

```
|q1(P)| ≤ w2          （两条：q1 ≤ +w2 与 −q1 ≤ +w2）
|q2(P)| ≤ h2          （两条）
 (P−C)·n ≤ 0          （一条：必须落在窗的室内侧）
```

关键点：`a1`、`a2` **不是单位向量、也不正交**——它们就是「被剪切过的轴」，这就是「斜」棱柱的全部代数。预先把 `a1·C`、`a2·C`、`n·C` 算好存在 portal 里，每个像素只剩点积。

#### 4.7.3 第 2 步：线段夹逼，得到 `[t0, t1]`

对射线 `P(t) = O + t·D`，每条不等式都变成 `t` 的一次式 `dot(O−C, a) + t·dot(D, a) ≤ b`：

```
s = dot(D, a);  c = b − dot(O−C, a)
s > 0  → t ≤ c/s        （上界）
s < 0  → t ≥ c/s        （下界）
s = 0  → 若 c < 0 则整条射线在体外，直接 return 0
```

5 组（q1 两条、q2 两条、平面一条）各给一个上下界，取

```
t0 = max(所有下界, 0)
t1 = min(所有上界, t_hit)        // t_hit = 该段 ray query 的表面距离
if (t1 <= t0) return 0;          // 绝大多数像素在这里被剔除，只花 ~12 次点积
```

`t_hit` 当上界这一步很关键：**它让「光束前方的物体」自动遮挡光束**，不需要额外阴影射线（见 4.7.5）。

**`t0` / `t1` 的准确语义**（容易说错）：

- 它们是**射线参数（单位方向 → 米）**，不是世界坐标；两端点位置要代 `P = O + t·D`。
- `t0` = 射线开始同时满足 5 条不等式的位置 = **进入光柱**；但三种情况下它不等于「进入」：
  - 相机本来就在光柱内 → `t0 = 0`（段起点，不是入射点）；
  - 主光线按现有代码带近裁剪面 → `t0` 可能被 `tmin` 夹住；
  - 被 `t_hit` 提前截断时根本不成立（无交集）。
- `t1` = **这段有效积分的终点**，通常**不是**「离开光柱」。三种来源：
  - 穿出侧面或穿回窗平面 → 这确实是「离开光柱」；
  - **被物体挡住 → `t1 = t_hit`，在光柱内部结束**（教堂里这是常态，墙/地板通常就在光柱里）；
  - 到达 `farPlane` → 光柱一直延伸出可见范围。

因为光柱是**凸的**（5 个半空间的交集），一条直线与它的交集一定是**单个连续区间**——这就是「5 次一维夹逼就够、不需要排序多个区间」的根本原因。若把多扇窗合并成一个点集就不再凸，会得到多段区间；本方案按 portal 分别处理，所以永远只有一段。

> 调试提示：调试图 ①（`RG = [t0,t1]/far`）应当用**未夹 `t_hit`** 的版本，才能看到光柱完整的截面；实际积分才用夹过的版本。

#### 4.7.4 第 3 步：4 点求积

等距取 `t_i = t0 + (i + 0.5)·Δ`，`Δ = (t1 − t0)/4`，每点算五个量：

| 量 | 公式 | 说明 |
|---|---|---|
| 透射 `T_i` | `exp(−τ_fog(0→t_i))` | §5.2 的解析高度雾；`τ` 一次 `exp` |
| 散射系数 `σs_i` | `β0·albedo·exp(−(y_i−y0)/H)` | 与 `T` 用的是同一个密度场 |
| 相函数 `p_i` | `HG(g, dot(L, D))` | `D` 是「眼→点」，`L` 是「点→太阳」；`g>0` 时迎光更亮 |
| 玻璃色 `K_i` | 常数，或投影取纹理（4.7.7） | 也可乘 alpha 阈值做花纹镂空 |
| 可见性 `vis_i` | 可选，1 条朝 `L` 的阴影射线 | 挡柱子/家具，见 4.7.5 |

```
贡献 = Σ_i  T_i · σs_i · p_i · K_i · E_sun · vis_i · Δ
```

量纲检查：`T`（无量纲）× `σs`（1/m）× `Δ`（m）= 无量纲 → 与辐亮度同量纲 ✓。光学薄时 `Σ T·σs·Δ ≈ σs·(t1−t0)`，正是「弦长 × 散射系数」，与 §5.14 的 `P` 同源。

#### 4.7.5 第 4 步：加到哪、谁负责遮挡（两件事分工）

```
// pathtrace.glsl 主循环，depth == 0 段的末尾
float shaft = fogShaftContribution(rayOrigin0, rayDir0, hit);  // 内部已把 t1 夹到 t_hit
radiance += throughput * shaft;                                // depth==0 时 throughput = 1

// 可选（等价于叠加形态 A）：让墙面也按同一密度衰减，能量上更自洽
// radiance *= fogTransmittance(origin, dir, t_hit);
```

**遮挡分成两类，各由不同的东西负责，不要混**：

| 遮挡类型 | 例子 | 谁负责 |
|---|---|---|
| 挡在光束**前面**（相机与光束之间） | 前景的柱子、人 | ✅ **`t1 = min(上界, t_hit)` 自动处理**，零成本 |
| 立在光束**里面/后面**（沿太阳方向挡光） | 光束穿过的柱子、拱券 | ⚠️ 必须靠 `vis_i` 阴影射线；不做就会「光柱穿过柱子」 |

从**中点取 1 个** `vis` 会让柱子投影变成「整束全黑」，很假；至少 2 个、最好 4 个（与求积点复用同一条射线的开销）。

#### 4.7.6 第 5 步：退化与边界（都要显式处理）

| 情况 | 处理 |
|---|---|
| 相机在光束内部 | `t0` 自然被夹到 0，照常积分 |
| 光束整个在表面之后 | `t1 ≤ t0` → 剔除（常见路径，代价 12 次点积） |
| `L·n ≤ 0`（太阳在窗背面/法线配错） | 直接跳过该 portal；编辑器里给出警告 |
| 太阳强度为 0 / 夜间 | `E_sun = 0`，整段跳过 |
| 多个 portal 在空间上重叠 | **各自独立相加**——它们是不同的光路，相加是正确的（不是重复计算） |
| 窗有花纹/镂空 | 用 `K_i`（含 alpha 阈值）逐样本判定；`K_i = 0` 的样本跳过 |
| 玻璃有厚度/吸收 | `K_i` 用 `traceShadowTransmission` 的等价近似（或一次玻璃 Beer 解析），不要两边都乘 |

#### 4.7.7 第 6 步（可选增强）：光束带花纹

每个样本把 `Q_i = P_i + τ(P_i)·L` 投到窗面，用 `(q1,q2)` 换算 UV，直接采样该窗的 `baseColorTex`（`pathtrace.glsl:119`）：

```
uv_i = (q1_i/w2, q2_i/h2) * 0.5 + 0.5          // → [0,1]
K_i  = texture(baseColorTex, vec3(uv_i * uvScale + uvOffset, texID)).rgb
```

成本：1 次点积 + 1 次除法 + 1 次纹理采样/样本。比走 `traceShadowTransmission` 遍历玻璃还便宜，而效果是「玫瑰窗的花纹浮在空气里」——教堂场景最值钱的细节。

#### 4.7.8 第 7 步：成本与档位

| 档位 | 每像素每 portal | 说明 |
|---|---|---|
| 最省 | ~12 dot + 4×(1 exp + 1 phase) | 无可见性、无花纹；光柱会穿过柱子 |
| 推荐 | + 2 条阴影射线 | 柱子有粗略投影 |
| 完整 | + 4 条阴影射线 + 4 次纹理采样 | 柱子投影准确、光束带花纹 |
| 极省 | 把 4 点降到 2 点 | 浓雾/宽光束下几乎看不出差别 |

4 条可见性射线**方向完全相同**（都是 `L`），是 SIMT 相干度的最好情况；与「随机选灯」的 NEE 相比，它的遍历开销小得多。

#### 4.7.9 自检（四张调试图，按顺序看）

1. **区间图**：`RG = [t0, t1] / farPlane` —— 能直接看出光束的截面形状（是不是被法线/剪切轴搞反了）；
2. **内外 mask**：`t1 > t0` 的像素涂白 —— 检查柱体是否在预期位置；
3. **可见性图**：`vis` 通过率 —— 检查柱子遮挡是否生效、有没有整片黑；
4. **单/全 portal 对比**：逐个开关 —— 检查多窗叠加是否过亮（这通常是 `K` 被乘了两次）。

#### 4.7.10 一分钟手算（轴对齐特例，用来确认理解）

取最简配置：窗在平面 `z = 0`，矩形 `x ∈ [−1,1]`、`y ∈ [5,8]`，外法线 `n = (0,0,−1)`；太阳方向 `L = (0,0,−1)`（指向 `−z` 的太阳），于是 `L·n = +1 > 0`，光从 `−z` 射向 `+z`（室内在 `z > 0`）。

代入 §4.7.2 的 `τ(P) = −(P−C)·n/(L·n)`：`(P−C)·n = −P.z`，所以 `τ = P.z`，落点 `Q = P + P.z·L = (P.x, P.y, 0)`。5 条不等式退化成：

```
−1 ≤ P.x ≤ 1 ,   5 ≤ P.y ≤ 8 ,   P.z ≥ 0
```

也就是说：**光束就是一个沿 `+z` 无限延伸的长方体棱柱**（注意它在光传播方向上没有「远端」，一直延伸到被几何挡住为止）。

现在追一条射线 `O = (0,6,−5)`、`D = (0,0,1)`：

| 不等式 | 代入 `P(t) = (0,6,−5+t)` | 得到 |
|---|---|---|
| `P.x ∈ [−1,1]` | `0` 恒成立 | 无约束 |
| `P.y ∈ [5,8]` | `6` 恒成立 | 无约束 |
| `P.z ≥ 0` | `−5 + t ≥ 0` | **`t ≥ 5`** |

所以 `[t0, t1] = [5, t_hit]`：射线从 `t=5` 进入光束，一直走到打中东西为止。若射线改成 `y = 9`（从窗上方走过），`P.y ∈ [5,8]` 不成立且与 `t` 无关 → `s = 0` 且 `c < 0` → **直接返回 0**，这就是「一秒剔除」的那条路径。

这个特例同时说明两件事：① 不等式组给的是**精确**的斜柱体（这里是正柱体），不是「用 AABB 保守包围」——没有虚警体积；② 判定「在不在」和求出「在哪一段」是同一个运算，后者才是真正要用的东西。

## 5. 推荐形态的技术设计（A → B → C 分层）

### 5.1 介质模型：指数高度雾

```
β(y) = β0 · exp( −max(0, y − y0) / H )          // 消光系数，单位 1/m
σs(y) = β(y) · albedo                           // 散射系数（albedo 为雾的颜色，向量）
```

- `β0`：基准高度 `y0` 处的消光（`1/m`）。参考量级：能见度 200 m 的轻雾 ≈ 0.015 /m，浓雾 ≈ 0.06 /m。
- `H`：高度衰减尺度（m），`H → ∞` 退化为均匀雾。
- `albedo`：单次散射反照率（雾的颜色）。`albedo = 0` 退化为纯吸收（形态 A）。
- 场景单位是米（Unity 默认），但**教堂模型的缩放未确认**，`β0` 与 `H` 的标定必须按实际包围盒做（§10.0）。
- **`y0` 建议设在场景最低点**（教堂地面或更低）。式子里 `max(0, y−y0)` 是「地面钳断」：低于 `y0` 之后密度不再增长、恒为 `β0`。一旦射线穿到 `y0` 以下，§5.2 的解析式与 §5.3 的反演都必须按 `y = y0` **把段拆成两段**（上段指数、下段常数）；把 `y0` 放进地面以下就能完全避免这个分支。

选指数高度雾的理由：解析可积（下面两节都用得到），一个 `β0 + H + y0` 就能表达「地面浓、高处淡」，且**不需要 3D 纹理**——直接绕开 §3.6 最贵的「加 binding」那一档。

### 5.2 解析透射率（每段/每条阴影射线只算一次）

设段起点 `a`、射线方向 `d`（已归一化）、段长 `L`，`dy = d.y`，`Δh = a.y − y0`：

```
|dy| > ε :  τ(L) = β0 · e^(−Δh/H) · (H/dy) · (1 − e^(−dy·L/H))
|dy| ≤ ε :  τ(L) = β0 · e^(−Δh/H) · L
T(L) = exp(−τ(L))
```

要点：
- 式子里 **不需要 `abs()`**：`(1 − e^(−x))/x > 0` 对正负 `dy` 都成立，向上看会饱和到 `β0·H/|dy|`，向下看会指数增长——这正是高度雾该有的行为。
- `dy → 0` 用第二式兜底，避免 `0/0`。
- 每条阴影射线一次（`maxT` 已知），**不需要 ray march**，约 10 flops + 1 次 `exp`。
- 前提是整段都在 `y ≥ y0` 之上。一旦穿到 `y0` 以下，按 §5.1 的说明把段拆开（上段用本式、下段 `β0·L`）；探针 `Tools/fog_math_probe.py` 的用例刻意都留在 `y ≥ y0` 之上。

### 5.3 自由程采样：解析反演（1 个随机数、无拒绝）

要按 `p(t) = β(t)·T(t)` 采样散射距离，可以对上面的 `τ(L)` 直接求逆：

```
u = rand();  τ* = −ln(1 − u)                       // 目标光学深度
A = β0 · e^(−Δh/H) · H/dy                          // |dy| > ε 时的渐近上限

若 τ* ≥ τ(Lmax)  → 段内无散射事件（射线继续走到表面 / 走到 farPlane）
否则 t = −(H/dy) · ln(1 − τ*/A)                    // 闭式，无迭代
|dy| ≤ ε 时：t = τ* / (β0 · e^(−Δh/H))
```

优点（相对 delta / ratio tracking）：
1. **零拒绝**：固定 1 次随机数、1 次 `log`，方差只来自「散射 / 不散射」这一个二值事件；
2. **权重是常量**：命中事件时 `throughput *= σs/β = albedo`，与 `t` 无关，不产生「按距离变化的权重」这种额外方差源；
3. 采样分布与真实消光完全匹配，**不需要 majorant 包围**，也就不需要 extra 的密度查询。

风险点：`A` 在 `dy → 0` 附近会溢出，因此实现时必须先判 `|dy| ≤ ε`（建议 `ε = 1e-4`，与现有 `EPS_VOLUME` 同量级，`pathtrace.glsl:17`）。这段数学**已在 CPU 上验证**：`Tools` 下的探针跑了 40 万次采样，无事件概率与 `T(L)` 偏差 3.9e-4（见 §10.0）。

**⚠️ 两套透射方案不能混用（本项目最容易踩的坑）**

「解析透射」和「自由程采样」是两套**自洽但互斥**的记账方式。距离采样时，透射率已经体现在「有多少比例的样本能走到那么远」这件事里（到达表面是一个概率为 `T(L)` 的事件），此时**再乘一次 `T(L)` 就是双重吸收**，画面会明显偏暗、还会随 `β0` 非线性变黑。正确的分工：

| 量 | 解析透射（形态 A） | 自由程采样（形态 B / C） |
|---|---|---|
| 主路径的段 | 显式 `× T(L)` | 采样 `t`；命中表面时**权重 = 1** |
| 散射事件 | 不存在（用求积近似 in-scatter） | `× albedo`（`σs/β`），与 `t` 无关 |
| 表面命中 | `× T` | `× 1`（不乘！） |
| miss / 天空 | `× T(far)` | `× 1`（不乘！吸收已由「能否走到 farPlane」隐式承担） |
| 阴影射线（NEE） | `× T(maxT)` | `× T(maxT)`（**这里必须显式乘**，因为它是独立采样的一条射线） |

读法：**只有阴影射线在两种方案下都要显式乘雾透射**。主路径上「乘不乘」取决于你选了哪套，混着用一定出错。

### 5.4 相函数与 NEE

- 相函数用 Henyey-Greenstein：
  `p(cosθ) = (1 − g²) / (4π · (1 + g² − 2g·cosθ)^1.5)`，`g ∈ [−0.9, 0.9]`；`g > 0` 前向散射（太阳光柱），`g = 0` 各向同性。
- 采样：`cosθ = (1 + g² − ((1 − g²)/(1 − g + 2g·u))²) / (2g)`，`g ≈ 0` 时退化为半球均匀。
- 散射点的 NEE **直接照抄现有结构**（`pathtrace.glsl:1110-1146` 灯分支 / `:1147-1188` 环境分支）：把 `bsdf_nee × NdotL` 换成相函数 `p(cosθ)`（`albedo` 已在散射事件处乘进吞吐量，这里**不要再乘一次**），其余（50/50 硬币、`×2.0` 补偿、`×lightCount`）不动。
- **环境项不要重复乘 `envIntensity`**：`environmentSample()` 返回的 radiance 已含 `envIntensity`（`pathtrace.glsl:881`），雾里若再乘一次就是双重计权。

### 5.5 与玻璃介质解耦：雾不进状态机

这是本设计最重要的一条：**不要试图把雾塞进 `isInsideVolume` 状态机**。

- 现有状态机是 1 bit（`pathtrace.glsl:946-947`），一旦雾和玻璃共用，就变成「雾在玻璃外 / 玻璃内还有雾」的嵌套问题，直接撞上 §3.2 的单介质假设；
- 正确做法：雾当作**全局无界介质**，用**独立的一套函数**处理（形态 A 用解析透射 §5.2；形态 B/C 用自由程采样 §5.3），玻璃内部的 Beer-Lambert 保持原样（`:1069-1070`）。两者是**相乘 / 串联**关系，互不干扰，`isInsideVolume` 一行都不用改；
- 于是「雾里的玻璃」自动正确（雾在外、玻璃在内，两者吸收相乘），「玻璃里的雾」也自动正确（物理上本来就是全局的）。

一句话：**雾是函数，玻璃是状态机；不要让它们共享状态。**

### 5.6 阴影射线：光束与彩色玻璃

现有 `traceShadowTransmission()`（`pathtrace.glsl:568-706`）已经做了：镂空跳过、玻璃按 Fresnel/透过率累积、体积玻璃的 Beer 段吸收、层数上限 16。它返回的是**彩色**透射率。

所以彩色光柱的实现是**免费**的：

```
shadowTrans  = traceShadowTransmission(...)          // 已有的彩色玻璃透射
shadowTrans *= fogTransmittance(origin, dir, maxT)   // 新增：解析高度雾，一次算完
```

不需要遍历雾、不需要 march、不需要第二套阴影逻辑。太阳穿过彩窗 → 玻璃给颜色 → 雾给光束，两件事各自独立。

⚠️ 这里有一个**必须绕开的既有缺陷**：`traceShadowTransmission()` 在遍历结束返回时**不补最后一段吸收**（`:700` 的注释明写「若射线漏出介质，不补最后一段吸收」）。对玻璃这是有意的近似（补了会把数值漏光变成黑点）；但对雾不能这么干——雾的段必须算到尾，否则光源方向永远不够暗，光束会偏亮。本设计**不去改那段逻辑**，而是让雾的透射用独立解析式按整条 `maxT` 一次算完，从而绕开 `:706` 返回值信息不足的问题（它只返回颜色，不返回「已走到哪」）。

### 5.7 miss 分支怎么改（取决于选哪套方案）

现有 miss 分支直接把环境色全额加进来（`pathtrace.glsl:1003-1006`），对玻璃来说这是有意为之（§5.6 的「不补尾段」）。加雾后：

- **形态 A（解析透射）必须补**：`radiance += throughput * envColor * T(剩余距离)`。不补的话，地平线方向会变成「自发光的白墙」——这是体积雾实现里最常见的翻车点。
- **形态 B/C（自由程采样）不要补**：透射已经由「样本能否走到 farPlane」承担；再乘 `T` 就是 §5.3 说的双重吸收，雾会黑成一片。
- 两种方案都必须保证 `t` 与 `farPlane` 的比较口径一致：`tmax = min(farPlane, t_fog)`，`t_fog > farPlane` 才算 miss。

> 一句话判据：**同一个像素上，雾的透射只能被算一次。**要么显式乘，要么靠采样，不能既乘又采。

### 5.8 G-buffer / RR guide 怎么处理

雾散射事件会**绕过**现有的 G-buffer 写入（只在 `depth == 0 && s == 0` 且命中时写，`pathtrace.glsl:1073-1087`），如果不处理，RR 会拿到未初始化/过期数据。建议：

| guide | 建议 | 理由 |
|---|---|---|
| `gbufferPosDepth`（深度） | **仍写命中表面的 `hitT`**（如果该像素有表面）；纯雾（无命中）写 `farPlane` | 保持「背景几何」的 reproject 语义，雾的轻微不匹配可接受；现有玻璃已用同样近似 |
| `gbufferNormalRough` | 仍写表面法线；纯雾写 0 | 与 sky 一致 |
| `diffuseAlbedo` / `specularAlbedo` | 雾主导的像素写 **0.5 灰**（与 sky 的处理一致，`pathtrace.glsl:995-999`） | 告诉 RR「这里没有材质」，避免它按表面 albedo 反推亮度 |

这些都是「近似”，**必须在 §10 的 A/B 里连同噪声一起看**；如果出现雾区拖影，第一件事就是改这里的语义，而不是加 spp。

### 5.9 终止与 maxDepth 预算

- 散射事件会**消耗弹射深度**。当前 `maxDepth` 默认 8（`PathTraceRendererFeature.cs:49` 字段），最近一次 Play 实际是 4（`Editor.log`）。加雾后建议 **P2 = 4 → 5**、**P3 = 4 → 7**，否则「有雾的房间会明显变暗」——因为本来该打到墙上的路径被雾截走了。
- 增加 **散射次数上限**（建议 4），与现有 Russian roulette（`pathtrace.glsl:1253-1259`）叠加。RR 只按 throughput 判断终止，浓雾下 `throughput ≈ albedo`（不衰减），会**永不终止**；这是必须加硬上限的原因。

### 5.11 主循环里「打中雾」是怎么判定的（没有求交，只有比远近）

这是整套方案最容易问倒人的一点：雾不在 TLAS 里，那怎么知道射线「打中」了它？

**答案：根本不判断「打中」。介质不是一个要命中一次的目标，而是一个「沿射线随时可能发生的事件」。所以每段只要让三个候选者赛跑，谁最近谁赢：**

| 候选者 | 来源 | 距离 |
|---|---|---|
| ① 表面 | 硬件 ray query | `hitT`（committed 命中） |
| ② 介质散射 | **我们自己采样** | `t_fog`（从密度分布里抽出来的自由程） |
| ③ 逃逸到天空 | 两者都没有 | `farPlane` |

主循环改造后长这样（变量名对齐现有代码）：

```glsl
// ── 每段开始：rayOrigin / rayDir / tmin 已就位 ──
float tSegEnd = farPlane;                          // 段终点（还不知道表面在哪）
float tFog    = sampleFogFreeFlight(rayOrigin, rayDir, tSegEnd);   // ≥ tSegEnd 表示段内无事件

// ★ 全部的「集成」就这一行：把 raytrace 的搜索范围缩到雾事件之前
rayQueryInitializeEXT(rq, tlas, 0u, 0xFF, rayOrigin, tmin, rayDir, min(tSegEnd, tFog));
// ... 现有 candidate 循环（镂空 / 玻璃透射）完全不变 ...

if (committed && hitT < tFog) {
    // ① 表面赢了 —— 雾在这一段没有散射事件 → 权重 = 1（不要再乘 T，见 §5.3）
    //    现有表面着色 + NEE 原样跑
} else if (tFog < tSegEnd) {
    // ② 雾赢了 —— 在 tFog 处散射
    vec3 P = rayOrigin + tFog * rayDir;
    // throughput *= fogAlbedo；相函数取样新方向；NEE（复用 §5.4 的灯/环境两分支）
} else {
    // ③ 谁都没赢 —— miss，逃逸到 HDR 环境（现有 :1003-1006）
}
```

三个关键点：

1. **`tFog` 是「采样」出来的，不是「求交」出来的。** 它不是几何量，而是从 `p(t) = β(t)·T(t)` 里抽的一个随机数（§5.3 的闭式反演，1 次 `log`）。所以「雾在哪」这个问题在介质里没有意义——只有「下一次散射大概在多远」。
2. **防止「穿过雾打到墙」这件事，靠的就是 `tmax` 被夹到 `tFog`。** 一旦 `tFog` 更近，ray query 在 `[tmin, tFog)` 里找不到任何表面，`committed == false`，自然落到分支 ②。反过来若表面更近，雾事件就自动作废——不需要任何布尔标记，也不需要「跳过雾继续找表面」。
3. **不需要额外记账的原因**：走到表面是一个概率为 `T(L)` 的事件。采样已经替你把「吸收」折算进概率里了，所以分支 ① 的权重是 1。这也是 §5.3 那张分工表里「表面命中 ×1」的由来。

**有界雾盒（L1）不一样：它确实有「区间」，但也不进 ray query。**

- 用 ray-AABB 求出盒子在射线上的 `[t0, t1]`，与当前段求交，把采样**限制在交集内**（盒外 `σ = 0`）；
- 盒内常数密度：`tFog` 依然可以闭式反演，只是要加一个「落点不能超出 `t1`」的判定；
- 多个盒子重叠：**消光相加**（`τ_total = Σ τ_i`）。做法二选一——切点法（把段按所有盒边界切成 ≤ 2N+1 段，每段内是纯指数或纯常数，逐段解析反演，无拒绝）或 §12.5 的 majorant + tracking；
- 注意：这里**没有任何「命中排序」**要处理，只有区间裁剪——这正是它比「进 TLAS」简单的地方（§12.8）。

**阴影射线完全不参与这场赛跑。** 它要的不是「沿途有没有事件」，而是「整段的透射率」，所以直接 `shadowTrans *= fogTransmittance(origin, dir, maxT)` 解析算完（§5.6）——它永远不会「打中」雾，只会被雾削弱。

**调试建议**：加一个 `fogDebugMode`，直接把 `tFog / hitT` 写到屏幕上。`< 1` 的像素就是「雾赢」的区域，一眼能看出雾与几何的分界面——这比打印任何数字都直观，也是排查 §7-5「透射记账混用」最快的办法。

### 5.12 走一遍：眼睛 → 红色光柱 → 墙壁

最容易被问住的具体场景：一条视线从相机出发，中途穿过一道**从上往下打下来的红色光柱**（彩窗透进来的阳光），最后打在墙上。没有步进，凭什么这一段会变红？

先把「红」是谁给的这件事拆清楚。**红不是雾给的，是彩窗给的；雾只负责「把太阳光转向眼睛」。**

```
                  ☀ 太阳
                    ╲
                     ╲  ← ③ 阴影射线：P → 光源，穿过彩窗 → 返回红色透射率
                      ╲
   👁 ──────①───────•────────②────────▩  墙壁
        rayDir       P (t = tFog)     hitT
                      ╲
                       ╲ ④ 相函数 p(θ)：θ 是「光线来向」与「视线去向」的夹角
```

一次样本里发生的六件事：

| # | 发生什么 | 用到的机制 |
|---|---|---|
| ① | 从相机沿 `rayDir` **采样**一个散射距离 `tFog` | §5.3 闭式反演（1 次 `log`） |
| ② | 把 ray query 的 `tmax` 夹到 `tFog`，确认 `tFog < hitT`（墙更远） | §5.11 的赛跑 |
| ③ | 在 `P = origin + tFog·rayDir` 处向太阳打一条**阴影射线**；它穿过彩窗，`traceShadowTransmission` 返回**红色**透射率 | `pathtrace.glsl:568-706` |
| ④ | 用相函数 `p(θ)` 加权（`g > 0` 时朝太阳看更亮） | §5.4；`cosθ = dot(toL, rayDir)`（`rayDir` 是「眼→点」方向，符号写反会让光柱在看向太阳时变暗） |
| ⑤ | 贡献累加：`throughput(×albedo) · p(θ) · L太阳 · T彩窗 · T雾` | §5.4 / §5.6 |
| ⑥ | 继续弹射（P3）或终止（P2）；该像素本轮结束 | §5.9 |

所以「怎么知道经过了红光」的答案是：**眼睛这条射线从来不知道**。它只做了一件事——在某个距离上「掷骰子」决定要不要散射。真正去看「这里有没有被红光照到」的是 ③ 那条**阴影射线**，红光是它在彩窗上「染」上的。

**为什么看起来像是有个「光柱」**：光柱不是物体，它是「**太阳可见性区域的体积**」在屏幕上的投影。对每个采样点问一次「太阳看得见吗」，可见的那些点就会亮；这些点连成一片，就是你看到的光柱。雾只是把这些点暴露出来——没有雾，这条视线什么都不会发生，直接看到墙。

**为什么 1spp 也能出光束**：单像素单帧只是一次二值判决（要么散射要么不散射），所以静止帧里光束是**稀疏的红色噪点**；但「散射概率场」本身是平滑的，相邻像素的采样点落在同一片可见体积里，于是时域累积（DLSS RR）之后才是一条连续的光柱。**这正是 §10.2 的 #4 是全案分水岭的原因**——如果 RR 压不住这种「稀疏点状」的噪声，光束就会一直闪。

**三条可选路线，对应三种观感**（这条决定了「要不要步进」）：

| 方案 | 有没有步进 | 观感 | 代价 |
|---|---|---|---|
| 形态 A 解析吸收 | ❌ 无 | **没有光柱**，只有远景变灰变暗 | 最低（1 次 `exp`） |
| **形态 B 距离采样单次散射**（推荐） | ❌ **无步进**——用一次随机采样替代积分 | 有光柱，1spp 下是稀疏噪点，靠时域收敛 | 中（0 条净增阴影射线） |
| 形态 B′ 解析求积单次散射 | ✅ **8 ~ 16 步**，每步一条阴影射线 | 光柱**零噪声**、帧间完全稳定 | 高（每像素 +8 ~ 16 条阴影射线，约 +3 ~ 8× 阴影成本） |
| （美术替代）半透明锥体网格 | — | 假光柱，不参与 GI/反射，边缘穿帮 | 低，但要额外资产，且 PT 里透明体积同样是难题 |

**数学上为什么「不步进」是对的**：要算的是

```
L = ∫₀^d_wall T(0,t) · σs(t) · p(θ) · L_in(t) dt   +   T(0,d_wall) · L_wall
```

蒙特卡洛把它换成「按 `p(t)=σt(t)T(0,t)` 抽一个 `t`，在该点算被积函数」——**期望值等于积分**。所以不是「省略了步进」，而是「用 1 次采样替代了 N 次求积」，代价从**系统性偏差为零但方差大**换成**方差为零但贵 8~16 倍**。

**顺带回答一个隐含疑问**：「墙为什么也被照红了？」——那是墙面自己的 NEE：墙面 → 太阳的阴影射线同样穿过彩窗，拿到红色透射率（`pathtrace.glsl:1140-1143`）。这条路径现在就有，不需要雾。雾对它的影响只是**变暗**（`T雾` 乘上去），不会让它更红。

### 5.13 采样到底在赌什么：光束是一个体积，不是一条线

看完 §5.12 很容易得出一个过强的结论：「必须让采样点恰好落在与彩窗、太阳共线的那条线上，才能抓到红光」。**共线的直觉是对的，但「线」必须换成「体积」，而且赌的东西和直觉不一样。**

**① 条件不是「共线」，是「P 落在太阳可见体积里」。**

从点 `P` 能看到太阳（经过这扇窗），等价于：`P` 到太阳的连线穿过窗口那块**面积**。把窗口的每个点沿太阳方向挤出，得到一个**柱体**（窗口是矩形时就是斜棱柱）。`P` 落在这个柱体里，阴影射线才会带着彩窗的颜色回来；落在外面，阴影射线直接被墙/结构挡住，贡献为 0。

所以光束的「宽度」就是窗口的尺寸，不是零。一扇 2 m × 3 m 的窗、太阳仰角 30°，柱体在视线方向的**穿行长度（弦长）通常是好几米**——不是一根针。

**② 关键的不对称：只有「距离」在赌，「看不看得见」是精确算的。**

这一点最容易被忽略：

| 随机的是什么 | 确定的/精确的是什么 |
|---|---|
| 散射点落在哪（`tFog`） | 平行光的方向 `toL`（固定，不采样） |
| 50/50 的「这次问灯还是问环境」硬币 | 从 `P` 到太阳的可见性（阴影射线**精确**求交） |
| — | 彩窗的彩色透射率（`traceShadowTransmission` 精确累积） |

也就是说，**我们从来不去「猜太阳在哪」**——平行光只有一个方向，NEE 直接用它打一条阴影射线。唯一的随机性就是「这颗子弹有没有落在柱体里」。

**③ 真正在赌的概率：柱体内那一段的光学厚度。**

设视线穿过柱体的弦长为 `L_beam`、雾的消光为 `β0`，则「这一帧在该像素上散射于柱体内」的概率是

```
P = 1 − exp(−β0 · L_beam) ≈ β0 · L_beam        （光学薄时）
```

代一组实际数字（`β0 = 0.01 /m`，`L_beam = 2 m`）：

| 量 | 值 |
|---|---|
| 单帧命中柱体的概率 | **≈ 2%** |
| 60 帧内至少命中一次 | **≈ 70%** |
| 120 帧内至少命中一次 | **≈ 91%** |

这解释了两件事：**为什么 1spp 的光柱是稀疏噪点**（98% 的像素这一帧什么都没发生），以及**为什么必须靠时域累积**（要 1~2 秒才收敛成连续光束）。

**④ 所以噪声的根源是「概率小」，不是「对齐难」。** 对应三种解法：

| 解法 | 做法 | 代价 |
|---|---|---|
| 提高命中率 | 雾调浓（`β0` ↑）、或让光束更粗（窗口大、太阳角度更斜） | 观感变了，不是纯技术解 |
| 时域平均 | 靠 DLSS RR 累积 60~120 帧（§10.2 的 #4 就是要验证这个） | 0 成本，但移动相机时累积窗口变短、噪声回升 |
| 换确定性求积 | 形态 B′：沿段 8~16 步，每步一条阴影射线 | 每像素 +8~16 条阴影射线（约 +3~8× 阴影成本），换来零噪声 |

**⑤ 附带：光束的颜色是「场」，不是常数。** 每个 `P` 的阴影射线可能穿过不同的玻璃（红的、蓝的、镂空的洞），所以柱体里不同位置的红/蓝配比不同；重叠的多层玻璃还会把颜色**相乘**（`pathtrace.glsl:640-663` 的透射率累积）。这也说明它不是「一条线上的一个点」——它是逐点不同的颜色场。

### 5.14 窄光束：自由程采样在这里会失效，以及怎么救

**结论先说：是的，而且不是「偶然看不到」，是「大概率必然看不到」。** 窄光束是自由程采样最脆弱的一档，原因有两重——**又暗，又噪**。

**① 先区分两种「窄」**（只有第二种是致命的）：

| 窄的类型 | 例子 | 后果 |
|---|---|---|
| **屏幕空间窄** | 远处细长的光缝，只占几个像素 | ✅ 没问题：受影响像素少，但每个像素的 `L_beam` 照旧，照样收敛 |
| **沿视线的弦长短** | 视向几乎垂直于光束轴（侧看细缝）、窗口很窄 | ❌ 致命：`P ∝ L_beam` 变小，且亮度也同比变小 |

一个很有意思的推论：**同一道光束，朝太阳看时最容易看到，侧看时最难看到**——因为朝太阳看时视线是**沿着柱体轴**穿过去的，`L_beam` 最长；而且相函数（`g > 0`）也在这个方向最强。两个效应同向叠加，所以「迎着光看才有丁达尔」不只是观感经验，是几何+相函数的必然。

**② 定量：要多少样本才不噪**

二值命中估计的相对标准差是 `sqrt((1−P)/(N·P))`，要压到 10% 需要

```
N ≥ 100 · (1−P)/P ≈ 100 / P          （P ≪ 1 时）
```

按 §5.13 的 `P = 1−exp(−β0·L_beam) ≈ β0·L_beam`，取 `β0 = 0.01 /m`：

| `L_beam` | 单帧命中率 `P` | 需要样本 `N` | 折算帧数（按 RR 等效 ~30 样本/帧） |
|---|---|---|---|
| 2 m（正常窗） | 2% | 5,000 | ≈ 167 帧 ≈ **2.8 s** |
| 0.5 m（侧看/窄窗） | 0.5% | 20,000 | ≈ 667 帧 ≈ **11 s** |
| 0.2 m（细缝） | 0.2% | 50,000 | ≈ 1,667 帧 ≈ **28 s** |
| 0.1 m（极窄） | 0.1% | 100,000 | ≈ 3,333 帧 ≈ **55 s** |

（「等效 30 样本/帧」是按 RR 的时空邻域粗估的量级，不是实测；但**趋势是硬的**：噪声 ∝ `1/sqrt(L_beam)`，宽度减半 → 样本翻倍。）

**③ 更致命的是能量，不只是噪声**

光学薄时，单次散射的辐亮度是

```
L_beam_radiance ≈ σs · L_beam · p(θ) · L_sun = β0 · albedo · L_beam · p(θ) · L_sun
```

亮度**与弦长成正比**。`β0 = 0.01`、`albedo = 1`、`L_beam = 0.2 m`、`p ≈ 1/4π`、`L_sun = 3` 时，光束亮度约 `4.8e-4`；而同一面墙的漫反射亮度约 `0.3·3/π ≈ 0.29`——**差约 600 倍（近 3 个数量级）**，这时不是「噪点闪」，是「根本没有」。同样的雾里，正常的 2 m 弦长也只有 `4.8e-3`（差 60 倍），已经偏暗了。现实中细缝光柱之所以能看到，是因为空气里有大量尘埃（`β0` 比清雾高一两个数量级）。

**④ 所以真正的解法不是「加 spp」，而是换采样分布**

| 手段 | 对窄光束有效？ | 代价 | 备注 |
|---|---|---|---|
| 提 spp | ⚠️ 线性改善，仍要几千样本 | 线性 | 最笨的一档 |
| 雾调浓（`β0` ↑） | ✅ 同时提升命中率**和**亮度 | 免费但改观感 | 现实中细缝光柱就是这么来的 |
| 时域累积 | ⚠️ 秒级才收敛，相机一动就退 | 免费 | 静止镜头可用 |
| 形态 B′ 确定性求积（8~16 步） | ✅ 与宽度无关 | 每像素 +8~16 条阴影射线 | 简单可靠，先上这个 |
| **支持域采样（棱柱 / 等角采样）** | ✅✅ **最优：方差与光束宽度无关** | 需要窗口几何 + 权重公式 | 见下 |

**支持域采样的做法**（针对「窗口 → 太阳」这种光柱）：

1. 把窗口矩形 + 太阳方向作为「光柱源」喂给 shader（每个源 4 个角点 + 方向，约 64B，和 §12.3 的雾盒同一个 SSBO 就能放）；
2. 对视线与柱体做**解析求交**（4 个平面裁剪），得到区间 `[t0, t1]`——注意这不是 ray query，是 4 次平面测试，零遍历；
3. **在 `[t0,t1]` 内均匀采样** `t`（而不是按自由程采样），权重改成 `T(t)·σs·p(θ)·L_sun·(t1−t0)`；
4. 于是「是否命中光束」不再是随机事件——**每次采样都在光束里**，方差只来自 `T(t)` 的缓慢变化，与光束宽度无关。

这是参与介质渲染里的经典手段（对点光源是 equiangular sampling，对面积光/窗口是沿着「入射辐亮度」分布采样），原始出处是 Kulla & Fajardo, *Importance Sampling Techniques for Path Tracing in Participating Media*, EGSR 2012（[论文 PDF](https://blogs.autodesk.com/media-and-entertainment/wp-content/uploads/sites/162/egsr2012_volume.pdf)）。现场如果反馈「细缝光柱看不到」，第一反应应该是切这套采样，而不是把 `β0` 调到 1.0。

**⑤ 工程建议**

- **P2 先做自由程采样**（简单、通用），接受「宽光束清楚、窄光束噪」；
- 一旦出现「细缝光柱不可见」的具体需求，**再上支持域采样**（它需要美术把窗口标出来，所以不适合一开始就强制）；
- 两条路可以共存：宽光束用自由程、被标记的光柱源用支持域采样，按像素决定用哪个，互不冲突。

### 6.1 先统一口径（这条必须先做）

工作区里存在两个互不相容的分辨率：

| 来源 | 数值 | 备注 |
|---|---|---|
| `doc/RT_pipeline整体切换可行性调研.md` §1、DLSS4.5 文档 | 渲染 **568×320** → Balanced(1.7×) → **967×544** | 日志口径 |
| `doc/程序化几何体加速结构接入Terrain可行性调研.md` §8、DLSS4.5 文档 telemetry | **960×540** | `MVExtent`，按 1.7× 应输出 1632×918，与前一行矛盾 |

本机当前 `Editor.log` 只有 `[PathTrace] PT 配置`（`maxDepth=4, spp=1, quality=1`），**没有 `[PT-GPU]` 段落汇总**（需要累计 180 帧才打印）。所以：

- 本节所有推算用 **568×320 = 181,760 像素** 作为基数，并给出 960×540 的对照列；
- **真实基线必须在 §10.1 里先量出来**，否则后面的百分比没有意义。

### 6.2 什么变了、什么没变

| 项 | 变了吗 |
|---|---|
| 每像素 closest-hit 光线数 | ❌ 不变（雾不新增光线，只把「命中表面」换成「在雾里散射」） |
| 每段 shadow ray 数 | ❌ 净不变（散射点的 NEE 替换了表面 NEE，仍是 1 条/段） |
| 每段新增数学 | ✅ 解析透射（~10 flops + 1 `exp`）+ 自由程反演（~10 flops + 1 `log`）+ 相函数（~10 flops + 1 `sqrt`）；形态 A/B 各用其中一部分，表里按**并集**取保守口径 |
| 弹射深度消耗 | ✅ 变多（散射算一次弹射）→ `maxDepth` 要加 |
| 带宽 | ❌ 不变（不读额外纹理） |
| RR 输入布局 | ❌ 不变（6 张 guide 一个都不改） |
| 描述符 / 资源 | ❌ 不变 |

**结论：这是「纯算术增量」，不是「带宽/光线增量」——对 3070 Ti 这种算术富余、RT 单元紧张的卡是好消息。**

### 6.3 每像素成本账（推算，未实测）

以 568×320、`spp=1`、`maxDepth=4` 为例：

| 项 | 现状 | 加雾后（形态 B） |
|---|---|---|
| 主光线 | 181,760 | 181,760 |
| 弹射光线（估 2.0/px） | ~364,000 | ~364,000 |
| NEE shadow ray（估 2.5/px） | ~454,000 | ~454,000 |
| 新增算术 | — | ~30 flops/段 × ~4.5 段/px ≈ 135 flops/px |
| 新增 transcendental | — | ~2.5 `exp` / `log` / `sqrt` 每组，合计 ~11 个/px |

按 181,760 px 算，新增约 **2.4 × 10⁷ flops + 2.0 × 10⁶ transcendental**。3070 Ti Laptop（约 17 TFLOPS FP32，`exp/log` 走 SFU 约 1/4 吞吐）下这部分理论耗时只有 **0.1~0.2 ms**——**真正的成本不在这里**。

真正的成本是**散射事件改变了路径形状**：

1. 原本「打到墙 → 墙面 NEE → 再弹射」变成「在雾里散射 → 散射点 NEE → 相函数弹射」，**每段仍只有 1 条 shadow ray，但段的分布更发散**，RT 的 incoherence 上升 → 硬件遍历效率下降（术语与实测见 §6.7；本机无 SER，`doc/RT_pipeline整体切换可行性调研.md` §5.3 的结论：发散负载在无 SER 下更吃亏）；
2. `maxDepth` 从 4 提到 5~7，等于弹射数 +25%~+75%。

综合估算：**同 spp 下 PT 段 +25% ~ +45%**；若 1spp 噪声不达标要提到 2spp，则 **+150% ~ +190%**。**以上全部是推算，未实测。**

### 6.4 本机推算表（未实测）

假设当前 PT 段为 2 ~ 4 ms（`doc/RT_pipeline整体切换可行性调研.md` §5.6 的假设值，该文档明写「没有实测，需 P0 基线确认」），总帧 16.7 ms：

| 形态 | 分辨率 | PT 段增量 | 加雾后 PT 段 | 加雾后总帧 | 判定 |
|---|---|---|---|---|---|
| A 解析吸收 | 568×320 | +5% ~ +10% | 2.1 ~ 4.4 ms | 16.8 ~ 17.1 ms | ✅ 安全 |
| B 单次散射 | 568×320 | +25% ~ +45% | 2.5 ~ 5.8 ms | 17.2 ~ 18.5 ms | ⚠️ 略超 16.7 |
| B + 2spp | 568×320 | +150% ~ +190% | 5.0 ~ 11.6 ms | 19.7 ~ 24.3 ms | ❌ 超预算 |
| C 真介质 | 568×320 | +35% ~ +60% | 2.7 ~ 6.4 ms | 17.4 ~ 19.1 ms | ⚠️ 需降 `maxDepth` 或降分辨率 |
| B 单次散射 | 960×540（2.85× 像素） | +25% ~ +45% | 7.1 ~ 16.5 ms | 23.8 ~ 33.2 ms | ❌ 不可行 |

**这张表最重要的信息**：形态 B 在 568×320 下勉强够，在 960×540 下不够；**「提 spp」是最贵的一刀，比加雾本身贵得多**。所以真正要控制的是噪声，不是算术。

### 6.5 什么程度算「严重」

沿用 `doc/RT_pipeline整体切换可行性调研.md` §5.6 的口径：

- PT 段 **≤ +50%**：可接受（本项目 PT 段占比不高，且 60 fps 目标还有余量）；
- 总帧 **劣化 > 10%**：需要降级（降 `maxDepth`、降雾的 `maxDistance` 截断、或只在相机静止时开 P3）；
- **触发 TDR**：不可接受。本项目刚在 `f63fc40` 修过一次 TDR（把 GPU 工作延迟到命令缓冲），加负载前必须保留现有的 watchdog 与设备丢失检测（`PathTraceRendererFeature.cs:180-192`）。

### 6.6 显存

+48B UBO，零额外 RT，零 3D 纹理。**可忽略**（相对 DLSS 已占的 ~137MB，`doc/DLSS4.5接入可行性调研.md` §3.2）。

### 6.7 术语：什么叫「Scatter 型」负载

本文 §6.3 与 §13 都用了「Scatter 型」这个词，它**不是 Vulkan 概念，也不是本文发明的**，而是 `doc/RT_pipeline整体切换可行性调研.md` §5.2 引用参考工程（`vk_gltf_renderer`）时的一类 **benchmark 场景分类**：

| 档位 | 参考工程里的场景 | 光线特征 | 代表内容 |
|---|---|---|---|
| **Scatter**（体积 / 强发散） | 体积散射样例 | 每条光线的下一步方向、深度、材质都不同；同 warp 的 32 个 lane 几乎不重合 | 雾、烟、体积光 |
| **Surfaces**（表面 / 相干） | 不透明 + 透射室内、地形 | 相邻像素打到同一面墙/同一材质，分支与纹理访问高度一致 | 本项目现有的教堂/室内 |

**它为什么决定性能**：路径追踪在 SIMT 上执行，一个 warp 的 32 个 lane 共享指令流。Scatter 型负载下 lane 之间打的材质不同、要采的纹理数组 slice 不同、阴影是否被挡也不同 → 分支发散、纹理 cache 命中率低、部分 lane 空转。硬件不会因此变慢「一个数量级」，但会白扔一截吞吐。

**为什么它和 RT pipeline 绑在一起**：Ada+ 的 SER（Shader Execution Reordering）能把散乱的 invocation 按命中点重新排队，让 warp 重新变整齐（原理见 RT 文档 §10.1，参考工程 `raytracer_interface.h.slang:207-234`）。所以参考工程里：

- **Scatter + RT pipeline + SER**：约 **2×** 快于 Ray Query；SER 单独贡献 **2.3 ~ 2.8×**；
- **Surfaces + RT pipeline + SER**：反而比 Ray Query **慢 10 ~ 30%**（SBT/CH/AH 的固定开销压过收益）；
- **本机无 SER**（`rayTracingInvocationReorderReorderingHint = NONE_EXT`，RT 文档 §5.3 实测）：按参考数据推算，连 Scatter 档的 RT pipeline 也会比 Ray Query **慢 15 ~ 40%**（RT 文档 §5.4）。

**和体积雾的关系**：加雾等于把负载往 Scatter 档推——雾里散射出的光线方向是相函数随机偏折的，每条路径的后续命中各不相似。这有两层含义：

1. **现在**（Ray Query、无 SER）：雾的成本里有一项「发散惩罚」，不能只按 flops 算。§6.3 的 +25% ~ +45% 已经把这部分折算进去，但它**无法单独标定**，只能靠 P0 基线 + 开关雾的 A/B 量出来。
2. **将来**（迁 RT pipeline）：雾正是 SER 最擅长的负载，所以「先做雾、再评估迁移」是对的——雾会让迁移的收益变大，而不是变小（§13）。

**⚠️ 三个容易混的「散射」**，读文档时请按英文/上下文区分：

| 词 | 指什么 | 在哪 |
|---|---|---|
| **Scatter 型** | 负载分类（光线发散程度） | RT 文档 §5.2、本文 §6.3/§13 |
| 体积散射（volumetric scattering） | 物理过程：介质把光转向 | 本文 §5.4 相函数 / NEE |
| scatter / gather | GPU 访存模式（非连续读写） | 与本调研无关 |

## 11. 结论

1. **可行，且是「小改动 + 高收益」的组合**：不需要新 Pass、新 RT、新 binding，只要 UBO + 主循环三处插入；彩色光束复用现成的彩色玻璃阴影透射，几乎是免费的。
2. **如果目标就是丁达尔效应，选形态 E（Portal 光柱，§4.6）**：3 ~ 4 人天、零噪声、零 RR 风险、窄光束也成立，代价是要标窗口；否则才走形态 B（单次散射，通用但会引入噪声），形态 A 是当天可见的第一步，形态 C 只在 RR 门槛通过后才做。
3. **最大风险不在渲染，在降噪**：1spp + DLSS RR 与体积雾噪声的匹配度，是全案唯一必须实测才能判定的东西。§10.2 的 #4/#5 两组 A/B 应当在写 P3 之前完成。介质数学本身已无风险——§10.0 的 CPU 探针验证了 τ、自由程反演、`T²` 偏差与 HG 归一化。
4. **两条「不要做」**：不要用 URP 的雾/深度（PT 路径下没有输入）；不要把雾塞进 `isInsideVolume` 状态机（会打破单介质假设）。
5. **两个待确认项**（写在这里，避免后人重查）：
   - `pathtrace.glsl:1006` 与 `:1185` 的环境辐亮度是否存在 2× 双计（无 pdf 型 MIS 权重）——若是刻意调校，雾的环境 in-scatter 应跟随；若是缺陷，雾会放大它；
   - NGX Vulkan 的 `ColorBeforeFog/ColorAfterFog` 是否真的被消费（头文件有、代码未接），这决定形态 D 是否是有效退路。

## 12. 场景接入：雾不是几何体，也没有加速结构

这一节回答三个实操问题：**雾怎么「放」进场景、它要不要进 BLAS/TLAS、能不能做出不均匀且有流动感的雾**。

### 12.1 为什么介质不需要加速结构

BLAS/TLAS 的语义边界很清楚：ray query 只回答「最近的表面命中 / 候选三角形」。介质**没有表面**，它贡献的是沿射线的一段积分（发射 − 吸收 − 外散射），所以：

- 雾**既没有 BLAS、也没有实例、也不该进 TLAS**；
- 把雾盒当 AABB 实例塞进 TLAS 会有三处硬冲突，而不是「多花点性能」：
  1. 主循环把任何 committed 命中当表面（`pathtrace.glsl:985-986`），盒子会提前终止表面遍历 → 雾后面的东西永远打不到；
  2. 阴影遍历把「出现 committed 命中」当不透明遮挡（`:701-703`），雾盒会把**所有**阴影判成全黑；
  3. 就算特判，也要给盒子加 candidate 分支、同时改主循环与阴影两处遍历、还要调 TLAS 实例 flags——而换来的只是「盒子的入射 `t`」，这个 `t` 用 6 次乘加就能算出来（ray-AABB）。
- 真正需要「空间加速」的只有**密度场查询**，而这三条路都不是 BLAS：
  - **解析包围盒裁剪**：≤8 个雾盒时逐个做 ray-AABB，O(1)；
  - **3D 纹理**：纹理采样本身就是硬件加速的密度查询（trilinear，O(1)）；
  - **froxel 网格**：视锥体素，HDRP 那条路（§4.4 的形态 D），用于大量体积或独立 pass。

一句话：**加速结构解决「和谁求交」，介质解决「沿这条射线积多少」——后者不需要前者。**「射线怎么算打中雾」的具体机制见 §5.11：不是求交，而是让「表面命中 / 介质采样 / 逃逸」三个候选者比远近。

### 12.2 三种表示，对应三类「形体」

| 类型 | 场景里是什么 | 密度函数 | 适合 | 需要纹理 |
|---|---|---|---|---|
| **全局薄雾** | 不是物体：Renderer Feature 上的参数 | `β(y) = β0·e^(−(y−y0)/H)` | 均匀盖住全场景、远景发灰 | ❌ |
| **局部雾团** | 空 GameObject + `FogVolume` 组件（挂个 BoxCollider 只为画 Gizmo） | 盒/椭球 falloff × 可选噪声 | 局部浓雾、可漂移、可多个 | ⚠️ 可选 |
| **体积云/复杂形状** | 同上 + 3D 纹理（VDB 烘焙） | 纹理调制 × 高度 | 翻滚、非均匀、有细节 | ✅ 必需 |

要点：`BoxCollider` 在这套设计里**只承担 Gizmo 与尺寸来源**，不参与物理、不进 PT、不进 BLAS——这与 `doc/PT管线与Unity物理系统调研.md` 的结论一致（PT 与 Unity 物理彻底解耦）。所以「没有形体」不是缺陷：雾本来就不该有形体，它的「形状」是数学定义的密度场。

### 12.3 Unity 侧怎么接：照抄两条现成通路

| 通路 | 现成范例 | 雾怎么用 |
|---|---|---|
| 启动时收集一次 | `LightManager`（`Awake` 里 `FindObjectsOfType<Light>`，`LightManager.cs:39-51`） | `FogVolumeManager` 收集 `FogVolume` 组件 |
| 每帧小数据上传 | `VPT_UpdateInstances`（`vpt_api.h:31`，`ModelManager.cs:1163-1194`） | 新增 `VPT_UpdateFogVolumes`，只上传「有变化」的盒 |
| 全局参数 | `VPT_CameraData` → UBO（§5.10） | 薄雾的 `β0/H/y0/albedo/g` 走 UBO，不进 SSBO |

建议的单盒布局（80B，std430，与 `VPT_Light` 32B 同风格、16B 对齐）：

| 偏移 | 字段 | 含义 |
|---|---|---|
| 0 | `centerRadius` vec4 | xyz = 中心（世界），w = 最大消光 `β_max` |
| 16 | `extentFalloff` vec4 | xyz = 半尺寸，w = falloff 指数（越大边缘越硬） |
| 32 | `albedoAniso` vec4 | rgb = 散射反照率，w = `g` |
| 48 | `windTime` vec4 | xyz = 风向量（m/s），w = 动画倍率 |
| 64 | `noiseParams` vec4 | x = 噪声频率，y = octave 数，z = 演化速度，w = 随机种子 |

新增一个 `binding = 18`（readonly SSBO）即可——这是**唯一**要动 §3.6 那 6 处硬编码下标的地方；`binding 0–17` 已占满（16/17 是 HDR 环境图与 alias 表）。盒内采样用 ray-AABB 求 `[t0, t1]`，把积分区间裁到盒子内部，盒外 `σ = 0`。

### 12.4 不均匀 + 流动：三层配方

| 层 | 内容 | 成本 | 能表达什么 |
|---|---|---|---|
| **L0** 全局薄雾 | 解析高度雾，`H` 取 150 ~ 400 m（近似均匀），`β0` 0.002 ~ 0.01 /m | ≈ 0（解析式，§5.2） | 整个场景均匀蒙一层、远景对比度下降 |
| **L1** 局部雾团 | 2 ~ 8 个盒/椭球，密度 = `β0 · falloff(d) · (1 + 噪声)`；风 = 移动中心或滚动采样坐标 | 每段每盒 ~10 flops | 成团的浓雾、贴着地面漂、进出房间 |
| **L2** 细节密度 | 3D 纹理 64³ ~ 128³ R8（2 ~ 16 MB），两张不同速度叠加 | 每段 8 ~ 24 次纹理采样 | 翻滚、絮状、非均匀细节 |

数学上分层是干净的：**多个介质的消光可以直接相加**（`τ_total = Σ τ_i`），所以 L0/L1/L2 的透射率相乘即可；只有「介质之间的互相遮挡/多次散射」被忽略——薄雾下可忽略，浓雾叠加时会有偏差（写进 §7 的风险即可）。

### 12.5 不均匀密度会推翻 §5.3 的采样方式（重要）

§5.3 的「解析反演自由程」只对**密度仅随高度变化**成立。一旦乘上噪声或 3D 纹理，就必须退回 **majorant + ratio tracking**：

```
σ̄ = 盒内密度上界（β_max，保守取值）
循环：
  t += −ln(1−u) / σ̄
  σt = sampleDensity(P + t·d)              // 纹理或噪声
  w *= (1 − σt/σ̄)                          // 透射率权重
  if (ξ < σt/σ̄) → 真碰撞，停止              // 散射事件
```

- **无偏**，支持任意密度（包括流动的纹理）；代价是每段 8 ~ 24 次密度采样，而不是 §5.3 的 1 次。
- 混合策略：**L0 用解析（零采样），L1/L2 才 tracking**。这是本方案能把成本压住的关键。
- 阴影射线同理：L0 解析；L1/L2 用 4 ~ 8 步近似，或干脆只算 L0——**这是一个显式的正确性取舍**，必须在实现时注释清楚，别让后人以为阴影是准的。

**成本阶梯（按「形状复杂度」逐级加价，别一步跳到底）**

| 密度模型 | 采样方式 | 每段成本 | 能做出什么 |
|---|---|---|---|
| 全局高度雾 | 解析反演（§5.3） | 1 次 `log` | 均匀薄雾、远景发灰 |
| **盒内常数密度** | 解析反演 + ray-AABB 裁剪 | 1 次 `log` + 6 ops/盒 | 有边界的均匀雾块（硬边） |
| 盒内 falloff（无噪声） | 近似解析（按平均密度乘壳厚）或 8 步求积 | ~8 次标量运算/盒 | 软边雾团、贴着地漂 |
| 盒内 falloff × 噪声 | ratio tracking | 8 ~ 24 次噪声求值 | 不均匀、有流动感 |
| 3D 纹理细节 | ratio tracking | 8 ~ 24 次纹理采样 | 翻滚、絮状 |

读法：**「有边界」不等于「要用 tracking」**——盒内常数密度依然可以解析反演，只要把积分区间裁到盒里。真正把成本推上去的是**噪声/纹理**，不是盒子本身。所以「先做几个硬边雾块」是一个几乎零成本的中间落点。

### 12.6 流动的雾 + DLSS RR：新的风险点

雾没有运动矢量，RR 用**表面** MV 做重投影。所以缓慢流动的雾会被 RR 当成「贴在表面上的东西」去累积，可能出现拖影或「糊成一团」。缓解手段（按优先级）：

1. **风速慢**：≤ 0.5 m/s，且方向稳定（不要让雾来回抖）；
2. **空间频率低**：做「大尺度团块漂移」，而不是「细碎絮状翻滚」；
3. **连续推进**：用 `fogTime` 连续累加，**不要**逐帧随机偏移（那是给 RR 喂噪声）；
4. 相机静止时才开 L2 细节。

这条必须进 §10.2 的 A/B：**静止 / 慢移 / 快移** 三档各录一段，看雾区有没有拖影。

| 参数 | 建议值 | 说明 |
|---|---|---|
| `β0`（L0） | 0.004 /m | 能见度约 250 m 的薄雾 |

### 12.8 为什么不把雾做成「程序化几何体」送进加速结构

一个很自然的提案：既然 `doc/程序化几何体加速结构接入Terrain可行性调研.md` 已经论证了「AABB 进 BLAS + shader 内 DDA」，那雾盒也有 AABB，为什么不照做？**因为地形与介质对加速结构的要求正好相反。**

| | 地形（表面） | 雾（介质） |
|---|---|---|
| 盒子的角色 | 加速结构找到的**遮挡面** | 只是积分区间的**裁剪框** |
| 需要什么 | **最近**一个命中（排序必须正确） | 沿射线**所有**区间，以及每段的**透射率** |
| 硬件给不给 | ✅ 硬件天生做这件事 | ❌ 硬件只说「命中 / 未命中」，永远不说「衰减了多少」 |
| 谁做积分 | shader 拿到 `t` 后算表面着色 | 无论有没有 AS，都得自己做体积积分 |

**第一条硬理由：加速结构解决「发现」，不解决「积分」。** 即使迁到 RT pipeline、写一个 intersection shader，它能做的也只是 `ReportHit(t)`——告诉你「介质从这里开始」。穿透过去衰减了多少、散射到哪里，仍然要 shader 自己算。所以「进 AS」从来不会让体积渲染变简单，只会让「找到体积」变简单；而找到 8 个盒子本来就是 48 次乘加（约 0.1% 的段成本）。

**第二条硬理由：在我们这套 ray query 架构里，「程序化 AABB」的语义是残缺的。** 没有 intersection shader，AABB 候选必须手动 `rayQueryGenerateIntersectionEXT(t)` 才成为命中；一旦成为命中，就会撞上现有两处「TLAS 里只有三角形」的假设：

- 主路径：`:965-968` 对非三角形候选直接 `continue`（**当前代码会静默忽略雾盒**）；
- 阴影遍历：`:587-590` 同样丢弃非三角形候选；且 `:701-703` 把「出现 committed 命中」当作不透明遮挡 → 雾盒一旦被 confirm，整条阴影判全黑。

要正确工作，就得：遍历 → 认出雾盒 → 用自己算的 `t_exit` 而不是硬件给的 `t_enter` → **再开一次 ray query（新 `tmin`）找真正的表面**。每个雾盒一次额外全量 TLAS 遍历。成本对比：

| 方案 | 每段的体积查询 | 额外光线/遍历 | 阴影语义 |
|---|---|---|---|
| **解析 / SSBO 列表（本文推荐）** | 8 盒 × 6 ops ≈ 48 ops | 0 | 直接乘透射率 |
| 程序化 AABB 进 TLAS | 每次遍历 1 个 RTIP，且**拿不到区间**，仍要自己算 ray-box | **N+1 次遍历/段** | 需改候选分支，否则全黑 |

**第三条：工程面会同时变复杂。** 现有 `VPT_InstanceData` 是 `{materialID, blasID, transform}` 的 1:1 绑定（`vpt_types.h:110-117`），BLAS 只按三角形几何构建（`vpt_scene.cpp`），`FORCE_OPAQUE` 也只对不透明材质设置（`vpt_scene.cpp:722-736`）。塞入雾 BLAS 意味着要引入「实例种类」判别、假材质标记、以及在两个热循环里做类型分派——这与 Terrain 计划（也要往同一个 TLAS 里放 AABB patch）会正面对撞：到那时 TLAS 里会同时有「三角形表面 / 地形 patch / 雾盒」三类，候选分支必须按 instance 自定义索引分派三次。

**提案里对的部分（不是全盘否定）**

1. **用 AABB 定义形状是对的**——本文 §12.3 的局部雾盒就是 ray-AABB 裁剪积分区间，只是不走 AS；
2. **「雾团多了需要空间结构」也是对的**——但正确的结构是**雾专用的加速**，不是表面 BVH。参考实现（pbrt-v4）给体积的加速是 `GridDensityMedium` + 一张**低分辨率 majorant 网格**，用于 null-scattering 的包围，与表面 BVH 完全分离（[pbrt-v4](https://github.com/mmp/pbrt-v4)、[PBR 4ed 第 11 章 Volume Scattering](https://pbr-book.org/4ed/Volume_Scattering)）。落到本项目的两条等价做法：
   - **3D 纹理的 max-density mip**：用 mip 1/2/3 的「砖块最大密度」做空域跳过，零额外结构；
   - **8³ 均匀网格掩码**：每格一个 bit（512 bit = 64B），先测线段穿过的格子，再进有密度的格子。

**什么情况下这个决定会翻转**（给判据，别靠感觉）：

| 条件 | 结论 |
|---|---|
| 雾团 ≤ 32、且大小相近 | ✅ 线性循环，不要 AS（当前状态） |
| 雾团 > 32 且尺寸差异大（小盒被大盒包住） | ⚠️ 上雾专用 grid / majorant mip，仍不要 AS |
| 迁移到 RT pipeline + 有 SER | ⚠️ 此时「体积作为 procedural primitive + intersection shader」才名副其实，可重新评估；但衰减依然自己算，收益只在「发现」 |
| 需要「任意点查询密度」（GI 采样点、探针） | ❌ AS 帮不上，只能纹理/解析 |

一句话：**把雾放进加速结构，是用一个「表面求交」的机器去回答一个「沿射线积分」的问题——机器会给出答案，但答非所问。**

## 13. 与其它调研的关系（一句话）

体积雾**不依赖** Terrain 加速结构，也**不依赖** RT pipeline 迁移；反过来，若将来迁移到 RT pipeline，雾属于「Scatter 型」负载（`doc/RT_pipeline整体切换可行性调研.md` §5.2 的参考实测：Scatter 场景在 RT pipeline 下约 2× 快，但依赖 SER，而本机无 SER）——**雾会让 RT pipeline 迁移的收益变大**，两者的正确顺序是先做雾、再评估迁移。
